# V0.2 Audit — v0.1 repository assessment

Date: 2026-09-13. Method: full test suite green, build clean, live
verification of every enforcement path (memory + Postgres), one joint
Ballast run, code + schema + docs read. No assumptions; the joint test
caught a real idempotency bug (fixed, 97630e0), which is evidence the
verification habit works.

## What works (keep, do not rebuild)

- Transaction state machine with saga semantics; illegal transitions
  rejected at the domain layer; terminal states terminal.
- Policy engine: deterministic, first-match-wins, human-readable why on
  every decision. Refund-tier demo behavior verified live repeatedly.
- Approval gate: require-approval actions never execute before grant;
  decide is operator-only (agent self-approval impossible by construction).
- Idempotency scoped to (org, transaction) with regression test.
- Hash-chained receipts verified after PG round-trip; append-only audit.
- Bearer auth (keyed agent + operator tokens, bcrypt-only, legacy fallback),
  agent-identity binding, per-credential rate limiting, CORS allowlist.
- Postgres backend with embedded migrations 001-005, boot recovery that
  reports (not abandons) open transactions.
- MCP proxy: register/list/call through the engine, unlisted-tool rejection,
  upstream failures fail honestly, tokens never returned/logged.
- OTel spans (policy.evaluate, action.execute, transaction.compensate),
  trace IDs on audit payloads and response headers, Jaeger in compose.
- Dashboard (overview, transactions+timeline, approvals, receipts, audit,
  agents, login gate), Python SDK, demos, CI, OpenTofu stack (validate-clean).

## What is incomplete (acknowledged stubs, not fake code)

- Native integrations are mocks (crm/stripe/email/fs/http/github/deploy).
  Labeled as such; boundary (`ToolHandler`/`Compensator`) is clean.
- Transaction recovery REPORTS open txns; no reconciliation that resumes or
  settles them, no EXECUTION_UNKNOWN state.
- Policy model is flat match rules; no versioning, no simulation endpoint,
  no priority-conflict semantics beyond first-match, no time/resource/
  classification-condition expressiveness.
- No authority grants: group membership + policy rules implicitly encode
  what v0.2 calls authority. Biggest architectural gap.
- MCP: HTTP transport only, catalog cached at registration, no tool-registry
  overrides UI, no per-tool classification admin beyond register-time map.
- Dashboard: no policy authoring, no audit search filters, no live updates,
  no Principals/Authority/Integrations sections.
- Single Python SDK only; no CLI; no webhooks; no receipt signatures;
  no approval expiry/reasons beyond free text; no metrics endpoint.

## What is unsafe (must fix in v0.2, ordered)

1. Upstream MCP tokens stored reversibly (no envelope encryption). Any DB
   read leaks third-party credentials. Needs key-management abstraction
   (local key dev, KMS-compatible prod) before real servers are registered.
2. No credential rotation/revocation API surface used in practice (columns
   exist: revoked_at) and no last-used metadata. Stolen-credential response
   today is manual DB edits.
3. Shell integration does not exist yet — good. When it arrives it must be
   allowlist-only with path/env/timeout policy, never a general shell.
4. SSRF posture is scheme-guard only (MCP register, generic HTTP mock).
   Registration-time fetching + future HTTP integration need allowlists.
5. Rate limiting is single-process memory; multi-replica deploy silently
   multiplies the budget. Fine for single-node v0.1, must be documented
   as a scaling limit, not discovered later.
6. Dashboard API token is public-env (browser-visible). Acceptable behind
   the login gate for operators; must not be presented as end-user auth.

## What remains unchanged in v0.2

Modular monolith; Postgres; deterministic policy core (extend, don't
replace); saga-not-ACID semantics; tenant-from-credential; receipt chaining
format (append signatures, don't reformat); OTel-first observability;
boring-Go readability rules.

## What should be refactored

- Split evaluation into authority-check then policy-check (currently one
  step), returning machine-readable reason codes alongside `why`.
- Policy storage: per-rule rows exist in memory model but PG uses
  policy_rules table already — converge on versioned policy sets
  (policy_sets table + version on receipts) rather than growing the flat row.
- `writeJSON` nil-slice handling is presentation-layer patchwork; stores
  should return empty slices. Minor; do while touching stores anyway.
- Dashboard API layer should move the operator token server-side (Next API
  routes) instead of NEXT_PUBLIC exposure. Small, real hygiene.

## What should be deleted

- Nothing structural. Dead code check: `policies.Evaluate` blank import in
  server.go (`var _ = policies.Evaluate`), `RedactURL` is used; the
  `dashboard/.next` and `__pycache__` artifacts on dev machines are
  gitignored — confirm before any public push. No TODO graveyard found.

## Major risks

- Scope: the draft v0.2 prompt lists ~10 milestones of team-sized work.
  Solo-founder risk is building all of it badly instead of four things well.
- Quiet-success failure mode: idempotency replay returns prior records with
  prior decisions — correct, but operators must be able to distinguish
  replay from fresh execution (receipt IDs help; UI should label it).
- Policy-complexity cliff: V2 conditions (time, resource, classification)
  can turn the readable engine into a mini-language. Cap expressiveness;
  simulation endpoint is the safety valve that keeps it operable.
- MCP trust: a malicious/compromised upstream server returns tool content
  that flows into receipts and future prompts. Content is evidence, never
  instruction — enforce at display and at any agent loop that consumes it.

## v0.2 scope decision (cut-down, in order)

- M1: Authority grants (model, API, UI read, enforcement before policy,
  reason codes) + credential rotation/revocation endpoints.
- M2: Execution uncertainty (EXECUTION_UNKNOWN, reconciliation worker,
  recovery-that-settles, audit-visible) + receipt signatures + verify util.
- M3: Policy V2 core (versioned sets, simulation endpoint, classification/
  time/resource conditions, change audit) + dashboard policy authoring (test
  mode included).
- M4: Integrations that matter (Stripe test-mode real, GitHub real,
  Postgres read-classified, HTTP with SSRF allowlist; shell allowlist-only
  or deferred) + upstream-token encryption + Ballast pairing productionized
  (persistent stack, governed-task docs).

Explicitly deferred: CLI, webhooks, risk budgets, trust telemetry/scores,
TS SDK, live dashboard updates, multi-replica limiter, K8s docs.
